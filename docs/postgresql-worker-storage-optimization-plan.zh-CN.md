# PostgreSQL 持久任务、独立 Worker、独立模型网关与存储接口优化计划

> 文档状态：P0 已在本地实现，通过自动化回归、Docker Desktop 镜像构建和隔离 Compose 端到端冒烟测试；完整故障演练与生产发布待部署环境执行
>
> 适用范围：Review Writer 公网多用户部署
>
> 核心原则：复用现有 PostgreSQL、任务表、阶段接口、产物版本、模型调用和计量代码；将任务执行与模型网关分别从公共 API 进程解耦；不建立第二套业务状态，不在本期引入 Redis、Celery、MinIO 或新的工作流引擎。

## 1. 背景与目标

Review Writer 当前已经具备 React 前端、FastAPI、PostgreSQL、用户与项目隔离、后台任务、不可变产物、依赖哈希、统一模型网关和调用计量。现有实现适合单 API 实例和小规模多人排队使用，但任务执行仍位于 FastAPI 进程内部，持久文件也依赖单机文件系统。

本次优化不重写七阶段业务流程，而是在现有实现上完成四项基础改造：

1. 保留 PostgreSQL 作为任务状态和产物元数据的唯一事实来源；
2. 将任务执行从 FastAPI 进程移到独立 Worker 服务；
3. 将文本和图像模型网关从公共 FastAPI 进程移到独立内部服务；
4. 为所有长期用户文件建立可切换存储接口，当前继续使用本地磁盘，后续可切换阿里云 OSS。

完成后，系统应支持：

- 公共 API 重启不改变 Worker 任务租约，也不切断 Worker 与独立模型网关的连接；
- Worker 异常退出后，任务可通过租约过期自动恢复；
- 文本、图像、MinerU 和导出任务可按负载分别扩容；
- 所有文本和图像供应商请求经独立模型网关执行统一限流、计量、幂等和审计；
- 多用户任务公平排队，单个用户不能长期占满执行槽位；
- 现有前端 URL、API 路由、阶段按钮、进度显示和产物版本逻辑保持兼容；
- 从本地存储迁移到 OSS 时，不修改各阶段业务代码，所有长期用户文件均可迁移。

### 1.1 实施优先级

本文描述完整目标，但不要求一次性全部实现。所有工作按以下优先级执行：

| 优先级 | 含义 | 上线边界 |
|---|---|---|
| P0 | 首期最小安全改造 | 独立Worker和独立模型网关投入使用前必须完成 |
| P1 | 公网稳定性强化 | P0稳定后尽快完成，可逐项上线 |
| P2 | 规模扩大后的性能与高可用 | 只有监控数据证明需要时实施 |

P0没有完成前，不得直接增加API副本或大幅提高Worker并发。P1和P2未完成不影响P0小规模公网试运行，但必须在管理员侧明确当前容量和已知边界。

## 2. 当前实现审核

### 2.1 已经具备的能力

| 能力 | 当前实现 | 本次处理 |
|---|---|---|
| 用户、项目和任务隔离 | PostgreSQL 记录用户与项目归属 | 保留 |
| 任务持久状态 | `queued/running/succeeded/failed/interrupted/cancelled` 等状态写入 PostgreSQL | 保留并扩展租约字段 |
| 任务进度 | 支持当前值、总数和部分结果 | 保留 |
| 幂等与重试 | 使用幂等键、操作键和 `retry_of_job_id` | 保留 |
| 产物版本 | 不可变 Artifact、内容哈希、依赖哈希和 current 指针 | 保留 |
| 模型网关 | 统一文本/图像调用、任务令牌、计量及用户并发限制 | 保留能力并迁移到独立内部服务 |
| 用户文件隔离 | `HostedWorkspaceManager` 按用户 UUID 和项目目录隔离 | 保留为本地实现 |

### 2.2 当前主要缺口

#### 任务执行与 API 耦合

当前 `JobService` 在 FastAPI 进程中创建 `DaemonWorkerPool`。HTTP 接口、模型网关和长任务共享同一个容器生命周期，因此：

- API 重启会中断运行任务；
- 无法在不复制 API 的情况下单独扩容任务执行能力；
- 多 API 副本启动时，现有“统一中断运行中任务”的恢复方式可能误伤其他实例上的任务；
- 文本、图像、MinerU 和导出任务无法独立设置 Worker 数量；
- 长任务容易占满全部线程，使其他用户长期等待。

#### 模型网关与公共 API 耦合

当前文本和图像模型网关与公共 FastAPI 运行在同一进程中。即使任务执行已经迁移到独立 Worker，公共 API 重启仍会中断 Worker 对模型网关的访问；未来增加多个 API 副本时，每个进程内的并发信号量也会分别计算，无法继续表达全站供应商并发上限。

因此本次选择更彻底的方案：将现有模型网关代码迁移为独立、仅内网可访问的服务。公共 API 继续负责用户、项目、工作流和管理入口；独立网关专门负责供应商凭据、路由、全局与单用户限流、幂等、重试、计量和结算。

#### 存储服务仍绑定本地路径

当前 `ArtifactService` 已经实现安全发布、版本和哈希，但底层直接依赖 `pathlib.Path`、本地目录和同文件系统原子移动。PostgreSQL 保存的是相对路径和元数据，而文件本体位于 Docker `review_state` Volume。除此以外，上传 PDF、MinerU 输出、Metadata、SVG 编辑结果、图像缓存和导出文件也仍以本地路径为主要访问方式。

这种方式适合单服务器，但不能直接支持：

- 多台 Worker 访问同一产物；
- 对象存储；
- 跨服务器故障转移；
- 云端签名下载 URL；
- 存储后端无感切换。

本次确认的长期存储范围覆盖全部用户持久文件，而不只覆盖 `WorkflowArtifact`。科学脚本工作目录、解压目录、渲染缓存和失败诊断等可重建临时数据继续使用 Worker 本地临时磁盘。

## 3. 不在本次引入的技术

为避免技术冗余，本次明确不做以下事项：

- 不引入 Redis 作为第二份任务状态；
- 不引入 Celery、RQ、Dramatiq 等新的任务框架；
- 不让 Prefect 接管网站用户任务；
- 不部署 MinIO；
- 不立即启动多个 FastAPI 副本；
- 不在首期部署多个模型网关副本；
- 不改变 React 页面路由或现有阶段接口；
- 不把用户任务拆成多个互相冲突的业务真相；
- 不在第一期直接迁移已有文件到 OSS。

PostgreSQL 足以承担本阶段的持久队列、领取锁和任务租约。只有出现多服务器、高频事件广播或数据库队列压力后，才单独评估 Redis。

## 4. 目标架构

```text
React 前端
    |
    v
公共 FastAPI API（认证、授权、项目、工作流、任务提交与查询）
    |
    v
PostgreSQL（任务队列、租约、进度、版本、依赖、用量）
    |
    +----------------------+----------------------+
    |                      |                      |
    v                      v                      v
Scientific Worker      Document Worker      独立模型网关
文本/图像/MinerU       DOCX/PDF/图表渲染    文本/图像供应商出口
    |                      |                      |
    +-----------+----------+                      v
                |                           模型供应商 API
                v
PersistentFileStorage
  - LocalPersistentFileStorage（本期）
  - AliyunOssPersistentFileStorage（后续）
```

公共 FastAPI 和独立模型网关可以继续使用 FastAPI 技术栈，但必须是不同进程和不同容器：

- 公共 API 是产品控制面，负责用户会话、权限、项目、七阶段接口、任务提交、状态查询、人工审核和文件访问授权；
- 模型网关是内部供应商出口，负责凭据解析、协议适配、路由、限流、重试、幂等、计量、结算和审计；
- Worker 是执行面，领取 PostgreSQL 任务、运行科学脚本、调用内部模型网关并发布产物。

### 4.1 单服务器首期部署

首期所有容器仍可以运行在同一台电脑或云服务器：

- `api`：一个实例；
- `model-gateway`：一个仅内网可访问的实例；
- `worker-scientific`：两个实例或一个实例内两个执行槽；
- `worker-document`：一个实例；
- `postgres`：一个实例；
- `pdf-renderer`：一个实例；
- `review_state`：API 与 Worker 共用的持久 Volume。

这已经实现公共 API、模型调用和长任务三种生命周期的隔离。公共 API 重启不会修改任务租约，也不会切断 Worker 与模型网关的连接。模型网关自身重启期间，Worker必须把尚未确认完成的网关请求作为可恢复状态处理，等待网关恢复后按请求幂等键重试。将来迁移 OSS 后，Worker 才具备跨服务器部署条件。

## 5. PostgreSQL 任务租约设计

### 5.1 数据字段

在现有工作流任务表上增量增加以下字段，不新建平行任务表：

| 字段 | 用途 |
|---|---|
| `queue_name` | 区分 scientific、image、mineru、document 等执行能力 |
| `claimed_by` | 当前领取任务的 Worker ID |
| `lease_token` | 防止旧 Worker 在租约失效后继续提交结果 |
| `lease_expires_at` | 当前任务租约到期时间 |
| `heartbeat_at` | Worker 最近一次心跳 |
| `attempt_count` | 实际执行次数 |
| `next_attempt_at` | 短暂错误后的下次可领取时间 |
| `priority` | 同一队列内的有限优先级，不允许无限抢占 |

迁移必须是可空、可回滚的增量迁移，旧 API 在切换前仍可读取原任务记录。

### 5.2 原子领取

Worker 使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 原子领取任务：

1. 只选择状态为 `queued` 且 `next_attempt_at` 已到期的任务；
2. 只领取 Worker 声明支持的 `queue_name`；
3. 同一事务内写入 `claimed_by`、`lease_token`、`lease_expires_at` 和 `running`；
4. 其他 Worker 跳过已锁定或已领取任务；
5. 任务的每一次可观察写入都必须同时匹配任务 ID 和当前 `lease_token`。

这样能够防止同一任务被两个 Worker 同时执行。

租约校验不能只用于最终成功提交。以下操作全部必须使用租约令牌作为 fencing token：

- 更新进度；
- 写入部分结果或检查点；
- 续租和心跳；
- 发布或切换当前Artifact；
- 标记成功、失败、取消或延后重试；
- 写入父任务汇总状态。

失去租约的旧Worker只能停止和清理本地临时目录，不能再修改任务、产物或模型请求状态。

`queue_name` 必须由服务端根据 `job_type` 映射，不能接受浏览器任意指定。领取任务后，Worker凭任务ID和当前租约向内部模型网关换取短期任务令牌；网关必须核对任务仍为 `running`、Worker租约仍有效、用户和项目归属正确，并根据任务类型限制文本或图像能力。供应商API Key只存在于模型网关，不写入任务Payload，也不传给科学子进程。

### 5.3 心跳与恢复

- Worker执行主管线程独立定时延长租约，不能依赖科学脚本主动报告进度；
- API 重启不修改任何正常 Worker 的租约；
- Worker 异常退出后，租约自然过期；
- 恢复器只回收租约已过期的任务；
- 有安全检查点的任务从检查点继续；
- 无安全检查点的任务创建一次受控重试；
- 已发布的不可变产物通过幂等键和内容哈希去重。

首期默认参数为：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| 租约有效期 | 120秒 | 足够覆盖短暂调度抖动 |
| 心跳间隔 | 30秒 | 由Worker主管线程独立执行 |
| 恢复扫描间隔 | 15秒 | 只扫描租约已经到期的任务 |
| 连续心跳失败阈值 | 3次 | 达到后停止发布新结果并进入安全退出 |

所有租约创建、续租、过期判断和`next_attempt_at`计算必须使用PostgreSQL服务器时间，例如`NOW()`，不能依赖API、Worker或模型网关容器的本地系统时间。参数允许由管理员部署配置调整，但必须满足心跳间隔明显小于租约有效期。

模型网关发出的短期任务令牌必须绑定当前租约代次。租约失效后，旧Worker即使仍持有旧令牌，也不能再发起新的模型调用或提交成功结果。对于租约失效前已被供应商受理、但本地尚未收到响应的请求，使用现有模型请求幂等记录完成对账，不能简单重复扣费。

必须移除“任意 API 启动时把全部 running 任务标记为 interrupted”的全局恢复逻辑。

### 5.4 取消和关闭

- 用户取消仍先写入 `cancel_requested`；
- Worker 在现有 `checkpoint()` 位置感知取消；
- 已完成的单项结果必须先持久化，再响应取消；
- 正常关闭时 Worker 停止领取新任务，并在宽限期内完成或保存检查点；
- 强制关闭后由租约恢复，而不是依赖进程内 Future。

### 5.5 可靠唤醒

PostgreSQL任务表始终是唯一持久队列。

P0采用简单可靠的低频轮询：

- Worker每2–5秒查询一次可领取任务；
- 加入少量随机抖动，避免多个Worker同时查询；
- 队列为空时允许逐步降低轮询频率；
- 数据库查询必须使用针对状态、队列、重试时间和创建时间的索引；
- 不依赖进程内通知，因此API或Worker重启后任务仍可被发现。

P2只有在轮询延迟或数据库负载经过监控证明成为问题后，再增加“两层唤醒”：

1. API提交任务并成功提交数据库事务后，发送`LISTEN/NOTIFY`通知；
2. Worker收到通知后立即尝试原子领取；
3. Worker同时保留带随机抖动的低频轮询作为可靠保底；
4. 通知丢失、Worker重连或数据库重启都不能造成任务永久滞留；
5. `NOTIFY`只负责加速唤醒，不携带任务真相，也不替代任务表。

`LISTEN/NOTIFY`不是P0或P1依赖，也不需要为任务唤醒引入Redis。

## 6. 独立 Worker 设计

### 6.1 代码复用

不复制阶段业务逻辑。将现有任务 Handler 注册集中为一个共享注册表：

```text
review_writer_api/job_handlers.py     任务类型与 Handler 映射
review_writer_worker/main.py          Worker 启动、领取、心跳和关闭
review_writer_api/routers/*           只负责验证与提交任务
```

API 和 Worker 可以使用同一 Docker 镜像、不同启动命令。这样避免维护两份科学脚本和阶段逻辑。

### 6.2 队列划分

第一期只划分必要队列：

| 队列 | 任务范围 | 初始并发建议 |
|---|---|---:|
| `scientific` | 检索后处理、Matrix、Blueprint、章节、初稿、终稿文本任务 | 2–4 |
| `image` | AI 重绘和总览图 | 1 |
| `mineru` | PDF 上传解析和 Metadata 构建 | 2 |
| `document` | DOCX、PDF和确定性图表渲染 | 1–2 |

队列并发与模型网关并发是两层限制：Worker 数量决定本地可执行任务数量，模型网关并发决定实际可同时访问上游供应商的请求数量。不能因为增加 Worker 就绕过统一网关限制。

### 6.3 多用户公平性

任务领取不能只按最早创建时间无限 FIFO。本次确认采用以下默认规则：

- 每个用户同时最多运行一个文本科学任务；
- 每个用户同时最多运行一个图像任务；
- 每个用户同时最多运行一个 MinerU 任务；
- 每个用户同时最多运行一个导出任务；
- 首期即使有空闲容量，也不提前运行同一用户的第二个同类任务；后续可由管理员显式开启；
- 优先选择当前运行任务较少的用户；
- 单项目批量子任务不能占满全部 Worker；
- 管理员任务也只能使用有限优先级。

用户可以继续提交超出并发额度的任务，超出部分进入队列而不是报错。全站各队列并发由管理员配置，任何管理员配置也不能绕过模型供应商的全局并发上限。第二个同类用户任务是否在全站空闲时提前执行作为后续可配置能力，首期默认关闭，以保证公平性。

这能避免某个用户提交全部章节或大量重绘后，其他用户完全无法开始任务。

### 6.4 独立模型网关

现有文本和图像模型网关能力迁移到独立内部 FastAPI 服务，不重新实现第二套计量或供应商配置。服务职责包括：

- 从 PostgreSQL 和服务端加密配置解析文本、图像供应商；
- 验证 Worker任务令牌、任务状态、用户、项目和租约代次；
- 执行文本与图像协议适配；
- 维护全站和单用户并发限制；
- 执行供应商错误分类、有限重试和退避；
- 复用现有请求幂等、用量计量、余额预扣、结算和审计记录；
- 向Worker返回规范化响应，不向Worker或浏览器返回供应商密钥。

首期只运行一个模型网关实例，因此现有进程内并发信号量仍可正确表达全站限制。模型网关不映射宿主机公网端口，只允许Compose内部网络访问。公共API中的管理员设置接口继续负责权限校验和写入加密配置，模型网关读取同一PostgreSQL配置；普通用户只能看到可用状态、模型档位和自身用量。

Worker中的科学子进程只获得：

- 内部模型网关地址；
- 短期任务令牌；
- 当前任务需要的非敏感模型参数。

模型网关重启或短暂不可达时，Worker保留任务租约和检查点，以有上限的退避等待恢复。只有超过任务允许的等待窗口才把任务标记为可重试失败，不能把已经完成的整批结果全部丢弃。

P0继续使用现有有上限的重试、错误分类、全局并发和单用户并发，不在首期实现复杂熔断状态机。

P1由于可能只有一个API中转站，网关增加按供应商与能力类型区分的基础熔断器：

- 连续出现429、502、503、504、连接超时或渠道不可用时，停止密集重试并打开熔断；
- 文本与图像通道分别统计，图像故障不能阻止纯文本任务；
- 熔断期间新请求进入`provider_deferred`或等价的可恢复等待状态，不占用供应商并发槽；
- 到达探测时间后只允许少量半开请求验证恢复；
- 探测成功后恢复有限并发，不瞬间释放全部等待任务；
- 已完成子项和检查点始终保留；
- 余额不足、模型不存在、协议不兼容和安全拒绝等确定性错误不能作为无限重试的短暂错误；
- 熔断状态、最近错误和下次探测时间必须在管理员后台可见。

P1熔断器状态可保存在PostgreSQL系统状态表，使网关重启后不会立即遗忘持续故障。它只表达供应商运行状态，不建立第二份任务事实。

P2在大量等待任务或多个供应商路由出现后，再实现按通道权重渐进放量、复杂探测策略和自动备用路由。P1不追求完整流量治理平台。

## 7. 长任务与子任务策略

第一期不强制把所有阶段拆成数据库子任务，但必须保留当前单项检查点和部分结果。随后按收益逐步拆分：

1. 每篇 PDF 的 MinerU 解析；
2. 每张图像的重绘；
3. 每个章节的生成；
4. 每个段落的评估与重写；
5. DOCX 与 PDF 分别导出。

父任务负责汇总：

- 总项数；
- 已完成数；
- 成功数；
- 延后重试数；
- 失败项 ID；
- 可继续执行的检查点。

单个子项失败不得默认终止其他相互独立的子项。涉及同一正文版本的串行写入操作仍必须保持顺序，避免覆盖用户刚保存的内容。

## 8. 存储接口设计

### 8.1 接口边界

新增无业务语义的存储接口，例如：

```python
class PersistentFileStorage:
    def put_file(self, source, key, *, expected_sha256): ...
    def materialize(self, key, target): ...
    def open_read(self, key): ...
    def exists(self, key): ...
    def stat(self, key): ...
    def delete(self, key): ...
    def download_reference(self, key, *, expires_in): ...
```

业务层继续使用资源ID、logical name、content SHA-256 和 lineage SHA-256，不直接判断存储后端。统一接口覆盖：

- 用户上传的原始PDF；
- 下载的论文PDF；
- MinerU输出及Metadata；
- Workflow Artifact及阶段产物；
- AI重绘和SVG/Ketcher编辑结果；
- 持久图像缓存和总览图；
- DOCX、PDF及发布清单；
- 其他不能从权威输入低成本重建的用户文件。

任务运行目录、解压目录、临时渲染文件、可重建缓存和诊断文件不属于长期存储。它们使用Worker本地任务专属临时目录，并在任务结束后按安全策略清理。

接入范围分级执行：

- P0：建立接口和本地实现，先接管Workflow Artifact、阶段输入物化和新生成的最终导出；
- P1：按模块接入上传PDF、论文下载、MinerU/Metadata、图像/SVG及其他长期用户文件；
- P2：实现OSS后端并迁移历史文件。

P0不能一次性重写所有路径调用。每接入一种文件类型，都必须先完成新旧读取一致性和历史文件兼容测试。

### 8.2 本地实现

`LocalPersistentFileStorage` 包装当前本地文件逻辑：

- 继续使用 `review_state` Volume；
- 保留安全相对路径校验；
- 保留同文件系统原子移动；
- 保留按用户和项目隔离；
- 不改变当前下载接口。

现有 `HostedWorkspaceManager` 继续负责本地用户目录安全，但上层Library、Artifact、Figure和Final服务不得再直接假定持久资源一定存在于某个宿主机路径。需要文件路径的旧科学脚本，由存储层把输入物化到Worker任务目录。

第一期上线只启用该实现，因此不会引入文件迁移风险。

### 8.3 OSS 实现的预留

后续 `AliyunOssPersistentFileStorage` 使用受用户和项目命名空间约束的对象 Key。科学脚本需要文件路径时，通过 `materialize()` 下载到任务专属临时目录，完成后发布产物并删除临时文件。Workflow Artifact保持不可变；允许编辑或替换的长期文件必须通过数据库版本或当前指针管理，不能覆盖无法审计的未知对象。

PostgreSQL后续可增量记录：

- `storage_backend`
- `storage_key`
- `etag`
- `size_bytes`
- `content_sha256`

已有 `relative_path` 在迁移期保留，禁止一次性破坏历史产物。

### 8.4 文件与数据库一致性

本地文件系统或OSS与PostgreSQL不能构成一个真正的跨系统事务。统一存储接口必须采用可恢复发布协议：

1. 将文件写入任务和资源归属明确的临时Key；
2. 计算并核对`content_sha256`、大小和媒体类型；
3. 使用当前任务租约创建或确认数据库资源记录；
4. 把文件提升为稳定Key，或将稳定记录标记为`available`；
5. 只有文件和数据库都验证成功后才能切换current指针；
6. 任一步失败都不能把不完整资源显示给用户；
7. 重试必须根据资源ID、内容哈希和幂等键复用已有成功结果；
8. 后台定期扫描超期临时文件、孤儿文件和数据库引用缺失对象，并生成只读审计结果。

本地实现可以继续利用同文件系统原子移动，但仍要处理“文件已经移动、数据库提交失败”的孤儿情况。OSS实现使用临时对象Key和数据库可用状态，不依赖不存在的跨系统原子重命名。

P0对新接入的Workflow Artifact和最终导出实现临时文件、哈希校验、数据库记录与current最后切换；P1再加入全部长期文件覆盖和简单孤儿审计；自动回收、不确定文件删除及跨存储修复属于P2，必须先生成审计报告，不能静默清除用户数据。

### 8.5 删除语义

本次保持现有项目删除交互和对外状态，不增加“待删除”业务状态，也不新增异步删除任务。删除操作改为通过统一存储接口执行，并继续满足：

1. 只删除经过用户、项目和资源归属校验的对象；
2. 不能通过用户输入拼接任意绝对路径或对象Key；
3. 同步删除失败时向调用方返回明确失败，不伪装成删除成功；
4. 数据库记录和文件删除顺序必须保留当前经过测试的回滚语义；
5. 删除成功后保留必要的安全审计，但不保留用户正文和文件内容。

正式接入OSS时，再单独设计对象存储的异步清理、失败重试、保留期和孤儿对象回收；该能力不属于本次首期范围。

## 9. API 与前端兼容策略

本次优化不改变用户操作流程：

- 原有任务提交接口继续返回 Job；
- `/api/v1/jobs/{id}` 的状态结构保持兼容；
- 重试、取消和部分进度继续使用当前接口；
- React页面仍可沿用当前轮询；
- 页面刷新后继续从 PostgreSQL 恢复状态；
- 后续如改为 SSE，只替换状态传输方式，不改变任务事实来源。

当前仅供科学子进程使用的内部模型路由从公共API容器迁移到独立模型网关，但它们不属于浏览器公开契约。公共站点URL和用户可见API保持不变。Worker环境中的网关地址必须使用Compose服务名，例如 `http://model-gateway:8782/...`，不能继续使用容器内的 `127.0.0.1:8770`。

### 9.1 功能保留清单

本次属于基础设施解耦，不得改变以下产品能力和用户操作语义：

- 注册、登录、退出和HttpOnly Cookie会话；
- 用户、项目、任务和文件隔离；
- 项目创建、选择、删除和恢复当前项目；
- 本地PDF批量上传、联网下载、MinerU与Metadata构建；
- 文献检索、审核、删除结果和Matrix；
- 大纲选择、上传学习、编辑、自动调整和Blueprint；
- 章节生成、单章检查点、实时进度与失败恢复；
- 图像候选选择、AI重绘、人工通过和全部通过；
- SVG/Ketcher编辑、文字、橡皮擦、线条、箭头、撤销和保存；
- 初稿编辑、单段评估、候选对比、批量安全优化和人工接受；
- 结论、总览图、最终稿、终稿审计和引用检查；
- DOCX/PDF生成、渲染检查和下载；
- 任务状态、取消、重试、页面刷新恢复和部分结果；
- Artifact版本、内容哈希、依赖关系、stale传播和人工审核；
- 管理员供应商配置、连接测试、模型档位、余额、用量和审计。

接口迁移遵循“新增能力→新旧路径一致性测试→小范围切换→完整回归→正式切换→最后清理旧路径”。数据库迁移只增加字段；公共API请求和响应契约保持兼容；历史文件首期不移动。任何阶段未通过功能保留测试，都不得删除旧兼容路径或进入下一迁移阶段。

前端可增加但不强制增加：

- 排队位置；
- 正在使用的任务队列；
- 因供应商限流而延后的状态；
- Worker恢复中的状态；
- 预计等待级别，而不是不准确的精确时间。

### 10.1 可观测性与故障演练

- job ID、user ID、project ID、Worker ID和租约代次关联字段；
- 队列总数、运行数和失败数；

- 各队列queued、running、deferred、failed数量；
- 最老等待任务及等待时长；
- 各Worker ID、能力、版本、最后心跳和当前租约；

- API、网关、Worker和镜像版本一致性。

P2只有在运维规模需要时，才接入独立指标平台、集中日志、告警系统和长期趋势分析。本计划不指定Prometheus、Grafana或其他新组件。

P0切换独立服务前必须完成最小故障演练并记录结果：

1. 长任务运行中重启公共API；
2. 模型请求期间重启模型网关；
3. 科学子进程运行时强制终止Worker；
4. 模拟中转站429、503和连接超时；
5. 验证恢复后无重复扣费、无跨用户数据、无重复current产物。

P1补充完整故障演练：

- 短暂暂停PostgreSQL连接；
- 模拟中转站空响应、协议异常和长时间故障；
- 模拟磁盘空间不足和文件发布中断；
- 从PostgreSQL和`review_state`备份恢复测试环境；
- 验证孤儿审计和缺失对象告警。

## 13. 上线与回滚

### 13.1 上线顺序

以下顺序只描述P0切换：

1. 备份 PostgreSQL、用户工作区和部署配置；
2. 执行只增加字段的数据库迁移；
3. 部署包含租约能力但仍使用旧执行器的版本；
4. 启动独立模型网关，将内部文本和图像调用切换到该服务并验证计量；
5. 启动独立Worker并做内部任务验证；
6. 在维护窗口关闭API内执行器；
7. 验证任务提交、执行、重试、取消和全部阶段；
8. 将Workflow Artifact、阶段物化和新最终导出切换到本地持久存储接口；
9. 观察队列、租约、网关和错误率后再逐步增加Worker。

P1每个强化项独立上线和回滚；P2在单独容量评审后实施，不与P0部署捆绑。

### 13.2 回滚原则

- 数据库迁移首期只增加字段，不删除旧字段；
- 如果独立模型网关异常，在数据库结构兼容期内可临时恢复原内部网关启动模式，但同一时刻只能启用一个全局限流出口；
- 如果独立Worker异常，先停止Worker，再恢复API兼容执行模式；
- 不回滚已经发布的不可变产物；
- 通过幂等键避免回滚后重复扣费或重复发布；
- 存储接口阶段首先使用新的本地实现且不移动历史文件，因此不需要同步迁回文件。

## 14. 验收指标

### 14.1 P0首期发布门槛

P0完成必须同时满足：

1. 公共FastAPI重启不会修改正常Worker的任务租约，Worker仍可访问独立模型网关；
2. Worker异常退出后，任务在租约到期后可恢复；
3. 同一任务不会被两个Worker同时成功提交；
4. 20个模拟用户提交任务时不存在跨用户数据访问；
5. 单用户不能持续占满所有Worker；
6. 原有任务API和React页面无需改变操作方式；
7. 七阶段功能、SVG/Ketcher编辑、独立模型网关、用量计量和DOCX/PDF导出全部回归通过；
8. `LocalPersistentFileStorage`读取现有Workflow Artifact、阶段物化输入和新最终导出时内容不变化；
9. 上游供应商并发始终受独立模型网关的全站及单用户限制；
10. 模型网关重启时，已完成请求不重复扣费，未确认请求可以按幂等键恢复；
11. 供应商密钥不进入Worker、科学子进程或浏览器；
12. 旧Worker失去租约后无法更新进度、部分结果、Artifact或任务终态；
13. Worker仅通过2–5秒低频轮询也能最终领取任务；
14. P0接入的文件在数据库或文件写入失败时不向用户显示不完整资源；
15. 第9.1节功能保留清单全部通过自动化或可重复人工回归；
16. 不新增Redis、Celery、第二套任务表或第二份业务状态。

### 14.2 P1强化验收

每个P1子项完成时分别满足：

- 中转站持续异常时基础熔断生效，等待任务不形成请求风暴；
- 上传PDF、MinerU/Metadata、图像/SVG等已接入文件类型保持历史兼容；
- 简单孤儿和缺失对象审计不会自动删除不确定用户文件；
- 管理后台展示的队列、Worker、网关和供应商状态与PostgreSQL一致；
- 完整故障演练中无重复扣费、跨用户数据或重复current产物。

### 14.3 P2启动条件

P2不是默认待办。必须提供监控证据，证明至少存在一项真实瓶颈：

- 轮询造成明显数据库负载或不可接受延迟；
- 单机本地存储无法满足容量、容灾或多服务器需求；
- 单公共API或单模型网关达到稳定容量上限；
- 当前日志和管理员监控无法满足运维需求。

## 15. 风险与控制

| 风险 | 控制措施 |
|---|---|
| Worker重复执行导致重复扣费 | 租约令牌、模型请求幂等键、任务令牌和请求记录共同校验 |
| Worker死亡后任务永久running | 心跳、租约过期和恢复器 |
| 旧Worker恢复后覆盖新结果 | 所有写入使用租约fencing token，数据库拒绝过期代次 |
| 公共API重启误伤任务 | 公共API不执行全局running状态重置，Worker租约独立存在 |
| 模型网关重启导致重复模型调用 | 短期任务令牌、请求幂等记录和供应商完成状态对账 |
| 模型网关成为单点 | 首期以有界重试和健康检查保证恢复；后续多副本前先实现分布式限流 |
| 一个用户占满队列 | 用户级运行上限和公平领取 |
| 增加Worker触发供应商503 | Worker并发与模型网关并发分离，网关限制不随Worker自动放大 |
| 中转站持续故障形成重试风暴 | 按文本/图像通道熔断、半开探测、渐进恢复和等待上限 |
| 历史产物无法读取 | 存储迁移先做代理，不立即移动历史文件 |
| 文件与数据库状态不一致 | 临时Key、哈希校验、available状态、current最后切换和孤儿扫描 |
| PostgreSQL通知丢失 | 通知只加速唤醒，低频轮询保证最终领取 |
| API、网关与Worker版本不一致 | 使用同一镜像标签，部署时先迁移再按兼容顺序统一滚动更新 |
| 本地磁盘损坏 | 单服务器阶段定期同时备份PostgreSQL和`review_state` |
| 过早引入复杂组件 | Redis、OSS和多API放在首期验收之后单独决策 |

## 16. 最终建议

本次优化应视为现有架构的解耦，而不是重建：

- PostgreSQL任务、阶段状态、产物版本和依赖关系继续作为权威数据；
- 现有Handler和科学脚本原样复用；
- P0将文本和图像模型网关迁移为独立内部服务，集中保管供应商密钥、限流、计量和结算；
- P0把执行生命周期从公共API移到Worker，并完成租约、防旧写、公平轮询和本地存储接口基础；
- P1再加入基础熔断、全部长期文件逐步接入、简单一致性审计和管理员监控；
- P2只有监控证明需要时才评估`LISTEN/NOTIFY`、OSS、多API、多网关、Redis和独立监控平台；
- 首期仍使用单服务器、单公共API、单模型网关和本地Volume。

这种分级顺序能够以最低技术冗余获得最直接的稳定性和并发收益，避免把完整生产强化路线误当作一次性交付，同时为后续公网多服务器部署保留清晰的扩展路径。
